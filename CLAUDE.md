# CLAUDE.md

## Project Overview

`nmg-sdlc` is a Claude Code plugin that provides spec-driven delivery for Claude Code and Herdr. Its manifest is `.claude-plugin/plugin.json`. Its hooks module `hooks/register.ts` (declared by `hooks/hooks.json`) registers the interactive `/sdlc-*` commands and enters native plan mode for them, and registers `/sdlc-execute`, which runs outside plan mode. The other automated commands are plugin command files under `commands/`.

## Repository Structure

```
.claude-plugin/plugin.json    # Claude Code plugin manifest (name + version)
hooks/hooks.json              # Declares the hooks module
hooks/register.ts             # Hooks module: interactive /sdlc-* commands and /sdlc-execute, plan mode, <plugin-root>, write-spec Continue/Finished, autopilot
src/host-events.mjs           # Node-free helpers shared by the hooks module and Node scripts
src/sdlc-*.mjs                # Workflow rendering, steering, verification, and prompt-snippet runtimes
commands/                     # Automated /sdlc-status, /sdlc-verify-code, /sdlc-open-pr command files (generated by renderAutomatedCommandMarkdown; never hand-edit)
workflows/                    # Private workflow files (one directory per workflow, WORKFLOW.md entrypoints)
agents/                       # Claude Code plugin subagents (starter, spec-implementer, architecture-reviewer, deliverer)
references/                   # Shared reference contracts loaded on demand by workflows
scripts/                      # Deterministic validators, status CLI, prompt renderer, exercise runners, and tests
specs/                        # BDD specs for the plugin's own development cycle (specs/{N}-{slug}/)
steering/                     # Product, tech, and structure steering documents
docs/decisions/               # ADR directory
package.json                  # Node package metadata (version mirror)
VERSION                       # Version source (kept in sync with package.json and .claude-plugin/plugin.json)
CHANGELOG.md                  # Keep an [Unreleased] section for pending changes
README.md                     # Public docs: workflow, installation, commands reference
.github/workflows/            # CI including contribution gate
```

Runtime state lives in the git-ignored `.nmg-sdlc/` directory of the project being worked on (handoffs, verification results, `run.json`, plans). It is never committed.

## Version Bumping

When bumping the version, update the root `VERSION` file, `package.json` `"version"`, and `.claude-plugin/plugin.json` `"version"` together. The delivery flow (via execute) keeps `VERSION`, `package.json`, `.claude-plugin/plugin.json`, and `CHANGELOG.md` in sync, using the version mirrors declared in `steering/snippets/project-tech.md`.

## README Updates

When making changes that affect how users interact with the plugin (new commands, changed workflows, new steering documents, etc.), update `README.md` accordingly. The README is the primary public documentation and must stay in sync with actual capabilities.

## Commit & CHANGELOG Conventions

- Conventional commits: `feat:`, `fix:`, `docs:`, `chore:`
- `CHANGELOG.md` uses `[Unreleased]` for pending changes; delivery rolls it to a versioned heading at release
- Workflows live in `workflows/{name}/WORKFLOW.md`
- `specs/` files must be committed with their feature branches, not left as untracked local files

## nmg-sdlc Spec Context

For SDLC work, project-root `specs/` is the canonical working-tree BDD archive and contains only current contracts with genuine GitHub issue owners. Specs use directories of the form `specs/{N}-{slug}/` where `N` is the GitHub issue number. Always identify the active spec first (leading directory number must match the issue and every file must declare singular `**Issue**: #N`), then use bounded relevant-spec discovery to load only the neighboring specs that can affect the change. Do not load the full archive by default. Superseded specs remain in Git history. A breaking repository rewrite may document unowned rewrite-only behavior in `references/rewrite-contract.{json,md}` but must not assign it a synthetic issue number or treat it as an executable issue spec. Legacy `.codex/specs/` directories are inputs to `/sdlc-upgrade-project` only.
